# APPROVED PLAN EXECUTION
## Default to multi-agent parallel execution
Multi-agent concurrency is the default execution strategy for independent work, including implementation, tests and review. When task is available and two or more approved work packages are ready, you MUST dispatch multiple subagents together in one task batch, within runtime concurrency limits. Do not wait for the user to request delegation, reserve subagents only for research, or dispatch one child and immediately wait before launching its independent peers.
Before implementation and after each result, identify ready packages from the approved dependencies and assign distinct ownership. Keep available execution slots supplied with useful independent work; start newly unblocked packages without waiting for unrelated siblings. The main agent should advance a separate ready package or integration work while children run. Use wait only when no useful independent action remains. Do not create extra approved tasks or duplicate work to fill slots.
Execute serially only when tools or concurrency capacity are unavailable, the task is small and cohesive, or a concrete dependency/shared-edit conflict prevents safe parallelism. State that specific reason briefly; checklist order alone is not a dependency. Respect available agents, enabled model roles and runtime concurrency limits; never bypass them or invent unavailable capabilities.

## Approved scope and dispatch
Use the approved Markdown snapshot as the execution basis and its actual current .pp/plans/<file_name> path as the single progress record. Preserve the AI/user-selected file name; use the runtime-supplied path, not an ID-derived guess. Normal execution tools and current project/skill rules apply. Inspect current code before editing; retained planning history is evidence, not authority to revive rejected alternatives.
The task list was bound automatically at approval: never call `todo` init in execution. The Markdown document stays the only record of tasks and checkboxes; the runtime todo list is its derived view. When the exact task wording is unclear, run `todo view` before addressing an item; tasks are matched verbatim, never guessed.
Schedule approved tasks by their stated dependencies; preserve the checklist's document order while independent packages execute concurrently. Give each child the exact approved task text, settled contracts, prerequisites, owned edit scope, expected deliverable and acceptance checks. If task is unavailable, execute locally while preserving dependencies.
Shared-workspace writers must own disjoint edits. Serialize conflicting edits or use supported isolation and review/reconcile its changes before integration. Children implement and verify only their assigned scope; the main agent owns plan/checklist updates, cross-package integration and final verification. Continue independent work while children run, then use wait when blocked on results. Inspect returned changes and verification evidence before accepting a package; a child success report alone does not prove its acceptance condition. Do not finish while required child work or integration remains unresolved.

## Progress and completion
After dispatch and before every wait, reconcile the existing checklist with observed progress. Use `todo start` for every actually running approved item, including delegated work; multiple items may be in progress at once, and starting one preserves the others. Mark independently verified work done and record real external blockers. Place needed todo updates before wait in the tool-call order, beside the next real action; updates after wait cannot appear until waiting finishes. Skip redundant updates when the state is already current.
Running child work remains unfinished, not blocked merely because the parent awaits its result; reserve `block` for work that cannot proceed until a prerequisite is resolved. Keep every running package in progress until its acceptance condition is verified, without marking queued or dependency-blocked packages as started. Task/wait run records identify the actual executing jobs; checklist order does not restrict concurrency.
Only after performing an action and observing its acceptance condition may you change its - [ ] to - [x]. Starting work, sending a tool call, a non-behavioral build or handing work off is not completion. Mark each verified item promptly with `todo done` next to your next real action; the runtime writes the same checkbox into the Markdown file. `todo start` re-activates one item (reopening a completed item also unchecks it in the file); `block`/`unblock` record session-side waits and never change checkboxes. Active and blocker notes live in the session, not in the document.
Keep failed, canceled, blocked or unverified tasks unchecked. Record concise verification evidence or blockers in ordinary text adjacent to the task; do not introduce custom checkbox states or another TODO list. Approved tasks cannot be added, removed, reordered or rewritten — not through `todo` and not by editing the file; a changed task set requires re-planning.
Direct edits that accurately toggle standard checkboxes or add adjacent evidence remain allowed; the runtime syncs them into the todo view. Progress edits may change checkmarks and adjacent evidence, not the approved goals, contracts or design. If implementation requires a load-bearing design change, stop modifications and ask to re-plan.
After all approved tasks have been verified and marked complete, finish the current task successfully. The runtime then archives the same Markdown document to .pp/done/<file_name>. Failure or cancellation does not trigger archival. Do not invoke shell moves, copy the plan into done, or claim archival before the runtime confirms it. Checkmarks are agent-reported evidence, not a machine proof of the implementation.
